# 五子棋游戏 —— 需求与实现步骤文档

> 版本：v1.0 ｜ 日期：2026-08-30 ｜ 状态：需求评审

## 1. 项目概述

### 1.1 目标
实现一个规则完整、架构清晰、体验良好的五子棋游戏，具备：
- 双人对战（本地同屏）
- 人机对战（内置 AI，分难度）
- 完整规则引擎（胜负判定，可选 Renju 禁手规则）
- 悔棋、存档、走子记录等辅助功能

### 1.2 技术选型（建议）

| 方案 | 技术栈 | 适用场景 |
|---|---|---|
| A（推荐） | HTML5 Canvas + JavaScript/TypeScript | 网页端，零安装易演示 |
| B | Python + Pygame | 桌面端，适合学习 |
| C | C++ / Qt | 高性能桌面端 |

说明：规则引擎与 AI 写成**纯逻辑模块**（不依赖 UI），可独立运行、可单元测试。

## 3. 规则基线（实现依据）

### 3.1 棋盘与坐标
- 15×15 交叉点，`(row, col)` ∈ [0,14]²；棋子落在交叉点而非格子内。
- 星位：天元 (7,7)，四星 (3,3)、(3,11)、(11,3)、(11,11)。
- 记录展示坐标约定：列 A–O，行 1–15（如 H8 = 天元）。

### 3.2 基本规则
- 黑先白后，轮流在空交叉点落一子，落子后不移动。
- **连五获胜**：任意方向形成连续 5 枚同色子。
- **满盘判和**：225 个点全满且无连五。
- 自由规则：黑棋长连（≥6）同样判胜。
- Renju 规则：黑棋禁手见 3.3；白棋长连判胜。

### 3.3 Renju 禁手（仅黑方，可选实现）

| 禁手 | 定义 |
|---|---|
| 长连 | 一子落下形成 ≥6 的连串 |
| 双四 | 一子落下同时形成两个及以上"四"（含冲四） |
| 三三 | 一子落下同时形成两个及以上"活三" |

- **成五优先**：若该手同时形成连五与禁手型，判胜不判禁。
- 黑落禁手点判负（或按产品需求提示"禁手禁止落子"，二选一并在 UI 说明）。
- 注意：活三/冲四的定义具有递归性（活三＝再一手可成活四；活四＝再一手可成五），是规则引擎最复杂的部分。

## 4. 总体设计

### 4.1 分层架构
```
┌─ UI 层：渲染、输入、动画、音效
├─ 对局流程层：回合、悔棋、存档、记谱
├─ 规则引擎层：胜负判定、禁手判定（纯逻辑）
├─ AI 层：候选生成 + 局面评估 + 搜索
└─ 数据模型层：棋盘、着法、状态

```

### 4.2 数据模型
```js
board = 15x15 二维数组   // 0=空, 1=黑, 2=白
move  = { r, c, player, index }
state = {
  board,
  turn: 1 | 2,
  history: [move, ...],
  status: 'playing' | 'black_win' | 'white_win' | 'draw',
  winLine: [{r,c}, ...]   // 连五子坐标，用于高亮
}

```

### 4.3 文件结构（Web 版示例）
```
gomoku/
├── index.html
├── require.md              # 本文档
├── css/style.css
├── js/
│   ├── model.js            # 数据模型
│   ├── rules.js            # 胜负/禁手判定（纯逻辑、可测试）
│   ├── game.js             # 对局流程
│   ├── ai.js               # 评估 + 搜索
│   ├── ui.js               # Canvas 渲染与交互
│   └── main.js             # 入口
└── tests/rules.test.js     # 单元测试

```

## 5. 详细实现步骤

### 步骤 0：项目初始化（0.5 天）
1. 建立目录结构，搭建 index.html 与 Canvas 容器。
2. 确定模块组织方式（ES Module 或普通 script）。
3. 验收：页面显示空白画布，控制台无报错。

### 步骤 1：数据模型（0.5 天）
1. `model.js`：`initBoard()`、`cloneBoard()`、`inBoard(r,c)`、`place(r,c,player)`、`remove(r,c)`。
2. 坐标换算工具：像素 ↔ 交叉点（`pixelToCell` / `cellToPixel`），注意吸附到最近交叉点。
3. 验收：初始化 15×15 全 0；克隆互不影响；坐标换算四角与中心正确。

### 步骤 2：规则引擎 —— 胜负与和棋判定（1 天）
1. `checkWin(board, r, c)`：从**刚落子点**出发，沿 4 条轴（横、竖、左斜、右斜）向两方向计数连续同色子，合计 ≥5 判胜（自由规则）。
2. Renju 模式：黑需**恰好 ==5**（长连转入禁手判定），白 ≥5。
3. 记录 `winLine` 坐标供 UI 高亮。
4. `isDraw(board)`：无空点且无连五。
5. 验收：通过第 6 节 T1–T6。

### 步骤 3：规则引擎 —— Renju 禁手判定（可选，1.5–2 天）
1. 线串提取：以某点为中心取 4 方向、长度 9 的窗口，编码为字符串（如 `0101110`）。
2. 模式匹配表：连五、活四、冲四（含 `10111`、`11011` 等断四形）、活三、眠三、活二。
3. `isForbidden(board, r, c)`：对黑候选点试落子，统计成五/成四/成活三数量 → 判长连、双四、三三。
4. 成五优先规则：先判成五，成五直接返回"胜"而非"禁"。
5. （进阶）活三/活四的递归严格定义；初版可用模式表近似，并在文档中注明近似边界。
6. 验收：通过第 6 节 T7–T9。

### 步骤 4：UI 渲染（1 天）
1. `ui.js` 绘制木纹底色、15×15 网格线、坐标标签、星位点。
2. 绘制棋子：径向渐变 + 阴影的黑白子。
3. 标记：最后一手红点、悬停半透明虚影、终局连五连线高亮。
4. 适配高分屏（devicePixelRatio）与窗口缩放。
5. 验收：棋盘无错位，点击吸附准确。

### 步骤 5：交互与对局流程（0.5–1 天）
1. `game.js`：点击 → 吸附最近交叉点 → 空点且未终局 → 落子。
2. 落子后：写 history → `checkWin`/`isDraw` → 切换回合 → 通知 UI 重绘。
3. 悔棋（人机模式回退 2 手）、重新开局按钮；终局弹窗。
4. 验收：完整双人局可下到连五/满盘，悔棋、重开正确。

### 步骤 6：辅助功能（0.5–1 天）
1. 存档/读档：state 序列化 JSON 存 localStorage。
2. 走子记录列表展示。
3. 动画与音效（可选）。
4. 验收：刷新页面后可恢复对局与记录。

### 步骤 7：AI 对战（2–3 天）
1. **候选点生成**：只考虑与已有子切比雪夫距离 ≤2 的空点；空盘直接天元。
2. **点评分（启发式）**：对候选点的 4 条线做模式匹配累加得分，评分表：

   | 棋型 | 分值 |
   |---|---|
   | 连五 | 10,000,000 |
   | 活四 | 1,000,000 |
   | 冲四 | 100,000 |
   | 活三 | 10,000 |
   | 眠三 | 1,000 |
   | 活二 | 100 |
   | 眠二 | 10 |
   综合分 = 己方进攻分 + 对方防守分×0.9（攻防兼顾）。
3. **杀棋快通道**：先扫描"己方一步成五 → 直接落"；"对方一步成五/活四 → 直接堵"，避免搜索浪费。
4. **搜索**：Negamax + α-β 剪枝 + 着法排序（按点评分取 Top N=8–10 扩展）：
   - 简单：深度 1 + Top3 随机扰动
   - 中等：深度 2
   - 困难：深度 4
5. 可选：Web Worker 中运行 AI，避免卡顿 UI。
6. 验收：AI 会堵活三/冲四、会做棋取胜；困难档单步 ≤3 秒；不落非法点。

### 步骤 8：测试、优化与发布（1 天）
1. 补齐第 6 节单元测试并修复缺陷。
2. 体验优化：提示文案（黑先/禁手/胜负/和棋）、按钮禁用态。
3. 编写 README（运行方式、功能列表、规则说明）。
4. 发布：静态托管（如 GitHub Pages）或打包桌面端。

## 8. 风险与注意事项
1. **交叉点落子**：五子棋子在交叉点而非格子内，像素↔坐标换算与吸附是高频出错点，务必单测。
2. **胜负扫描**：必须覆盖 4 个方向、双向计数并处理边界；只从最后落子点检查即可，勿全盘扫描浪费性能。
3. **禁手递归定义**：三三/四四的严格判定是递归的，朴素实现极易错；建议模式表 + 有限递归，并用已知棋谱用例验证。
4. **AI 性能**：裸搜 15×15 全空点会指数爆炸；必须限制候选点（邻域 ≤2）+ 着法排序 + 剪枝。
5. **评估函数攻防失衡**：只算进攻分会导致 AI"只攻不守"，防守分权重需反复调参对局验证。
6. **规则口径**：自由规则与 Renju 规则胜负口径不同，产品上需明确默认规则并在 UI 中展示说明。
